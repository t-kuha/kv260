# AMD EDF Linux for the KV260 acceleration platform

This flow uses AMD EDF **26.06.1** (Vivado/Vitis **2026.1**) and the hardware
handoff at `../hw.xsa`. It generates a custom `kv260-accel-sdt` machine from the
XSA, using the K26 starter-kit SOM and KV260 revB carrier device trees. The revB
carrier definition also covers the later rev1/rev2 carrier compatibles.

The Linux image is `edf-linux-disk-image-kria`, with XRT/ZOCL and Kria utilities
including `xmutil`. PL devices are placed in a separate overlay (`-g full`), so
Linux boots before application hardware is loaded. This XSA is an extensible
acceleration platform; it does not contain the final application bitstream.
This build omits the optional Kria telemetry dashboard and its Bokeh/contourpy
dependencies; the accelerator runtime and `xmutil` remain included.

## Host setup

Use Ubuntu 24.04 and a fresh Bash shell without sourcing Vivado, Vitis,
PetaLinux, or a cross-compilation SDK environment. SDTGen is invoked directly.
The default AMD installation is `/home/imagingtechnerd/amd/2026.1`; set
`AMD_TOOLS_DIR` to change it.

Install the [Yocto host dependencies](https://docs.yoctoproject.org/scarthgap/ref-manual/system-requirements.html#required-packages-for-the-build-host).
This host also needs `mtools` for disk-image operations. The build uses four
parallel tasks, removes recipe work directories after packaging, and stops
starting tasks if less than 8 GiB remains free. Downloads and caches still need
substantial space.

On Ubuntu 24.04, BitBake needs permission to create user namespaces. The
workspace-specific `bitbake.apparmor` profile (generated by `./build.sh setup`) grants this to this workspace's
BitBake executable. Generate and load it with:

```shell
./build.sh setup
sudo apparmor_parser -r bitbake.apparmor
```

The profile is loaded into the kernel only, so reload it after reboot. If the
workspace moves, update the executable path in the profile. The machine
generator runs under this same profile because it invokes BitBake via Python.

## Build

From this directory:

```shell
./build.sh
```

The stages can also be run separately:

```shell
./build.sh setup       # Download pinned EDF sources
./build.sh sdt         # XSA -> System Device Tree handoff
./build.sh configure   # SDT -> custom machine, FSBL/PMU multiconfigs, PL overlay
./build.sh build       # BOOT.BIN and EDF Linux disk image
```

Sources, downloads, caches and build output live in `_work/`. The generated
machine configuration lives in `meta-kv260/conf/`. These generated files are
ignored by Git and can be recreated with the script. The resolved source
manifest is `_work/manifest.lock.xml`, and `_work/hardware.sha256` records the
XSA used to generate the handoff.

After a successful build, `images` links to
`_work/build/tmp/deploy/images/kv260-accel-sdt/`. Look there for the
`edf-linux-disk-image-kria-*.wic.xz`, its `.wic.bmap`, the kernel, device trees,
and boot firmware artifacts. Firmware for the FSBL and PMU is also deployed
under the corresponding multiconfig `tmp-*` directories.

The KV260 normally starts its boot firmware from QSPI, then boots Linux from
microSD. The SD image and QSPI firmware must support the same boot flow; simply
putting BOOT.BIN on the SD card does not replace the board's QSPI firmware.
This Linux-only machine builds BOOT.BIN separately and omits the full
`kria-qspi` bundle, which the upstream recipe restricts to multidomain machines.
No flashing is performed by this build script. Load a matching application
bitstream and overlay before running an accelerator.

See AMD's [custom hardware flow](https://edf.docs.amd.com/en/latest/hwdev/custom-hardware-development.html)
and [Yocto environment setup](https://edf.docs.amd.com/en/latest/yocto/setting-up-the-yocto-environment.html).
